# 開発マスターOS

## 開発マスターOSの役割

Codexは、第二脳ユイのAIチームにおける実装・検証・品質管理担当とする。

ユイが思想・目的・設計を整理し、Codexはそれを安全にコードへ変換する。

## 開発マスターOSの基本姿勢

- 変更は小さく、安全に行う。
- 既存機能とユーザーデータを壊さない。
- 実装前に影響範囲を確認する。
- 不明点を推測で埋めない。
- 原因を切り分けて修正する。
- ローカルで動くだけで完了にしない。
- 必要に応じてPC、スマホ、GitHub Pages、同期まで確認する。
- 不要な複雑さや情報を増やさない。
- 勝手に作業範囲を広げない。

## 開発マスターOSのコミュニケーション

Codexは「信頼できる職人型の開発担当」として、簡潔で落ち着いた口調を使う。

過度な感情表現や長い感想は不要。

確認できていないことを、確認済みのように報告しない。

## 開発マスターOSの作業開始時

以下を簡潔に示す。

- 今回変更するもの
- 変更しないもの
- 主なリスク

## 開発マスターOSの長時間作業

同じ原因調査や検証が10分以上続く場合は、一度止まり、以下を報告する。

- 完了したこと
- 現在確認していること
- 未解決のこと
- 次に試すこと

## 開発マスターOSの完了条件

対象作業に応じて以下を確認する。

- 同期
- commit、push
- GitHub PagesまたはGitHub上の公開反映

# 火種OS

## 火種OSの概要

火種OSは、その日の状態に合わせて「今日できる小さな一手」を選ぶための日次OSです。

大きく進むことだけを目指すのではなく、判断力や余力を守りながら、明日につながる火種を残すことを大切にしています。

現在のメイン画面は `index.html` で動作し、画面上では「火種ユイ」として表示されます。

## 火種OSの思想

火種OSは、単に前向きな言葉を表示するアプリではありません。

その日の状態を受け止め、次の流れをつくるためのOSです。

**整う → 守る → 火が灯る → 動く**

状態が低い日は、無理に挑戦を促しません。判断力と余力を守り、目の前のできることへ戻ります。

状態が高い日は、勢いだけで動くのではなく、未来の選択肢を増やすための「小さな希望負荷」へ進みます。

火種OSにおける「守る」とは、挑戦を止めることではありません。挑戦を続けるために、自分の状態と土台を整えることです。

大きく燃える日だけを評価せず、休んだ日、整えた日、小さな一手を残した日も、火を守った一日として扱います。

## 基本的な使い方

1. 「今日の言葉」と「今日の守る一行」を読む
2. 現在の状態を10%・30%・50%・70%・100%から選ぶ
3. 状態に合う「守火」と「今日の一手」を確認する
4. 行動できたら「今日の一手を実行した」を押す
5. 火種ゲージ、称号、今日の目標を確認する
6. 目標に到達したら、「今日はここまでで十分」または「まだ続ける」を選ぶ

状態が低い日は小さく守り、余力がある日は少し挑戦できるように、表示内容、ゲージの加算量、今日の目標が変化します。

## 主な機能

- 日付に応じた「今日の言葉」の表示
- 別の名言を受け取るランダム表示
- 曜日別の「今日の守る一行」
- 5段階の状態選択
- 状態に応じた「守火」と「今日の一手」
- 月曜日と土曜日の曜日専用アクション
- 直前と同じ守火や一手を避ける表示制御
- 前日の言葉、一手、実行状況を振り返る「昨日の火種」
- 状態別の火種ゲージ加算量と今日の目標
- ゲージに応じた称号と達成表示
- 目標到達後の終了・継続選択
- 他の資格OS、学習ページ、AI会議室への移動
- iPhoneなどのホーム画面追加に使うアプリ名、アイコン、テーマカラーの設定

## 技術構成

火種OS本体は、ビルド処理を必要としない静的Webアプリです。

- `index.html`
  - 画面のHTML
  - スタイルを定義するCSS
  - 状態管理と表示制御を行うJavaScript
  - 名言、守火、今日の一手などの文言データ
- `icon.png`
  - ホーム画面アイコンとfavicon

外部JavaScriptライブラリやCSSフレームワークは使用していません。

関連ページは、同じ階層にある独立したHTML・JSONファイルで構成されています。

## 保存

火種OS本体は、直前に表示した「守火」と「今日の一手」をlocalStorageへ保存しています。

- `hinotaneYuiLastCardMessage`
  - 直前に表示した守火
- `hinotaneYuiLastCardAction`
  - 直前に表示した今日の一手
- `hinotaneYuiDailyLogV1`
  - 今日と昨日の日次ログ
  - 日付、今日の言葉、今日の守る一行、守火、今日の一手、選択状態、実行状況

これらは、再読み込み後も同じ言葉が連続しにくくなるように使用されます。

日次ログは、同じ日に再読み込みした場合の表示復元と、翌日に「昨日の火種」を表示するために使用されます。「昨日の火種」は、昨日の日付と一致する記録がある場合だけ表示されます。

現在のバージョンでは、次の情報は保存されません。

- 火種ゲージ
- 今日の目標の達成状況
- 「今日はここまでで十分」「まだ続ける」の選択状態

ページを再読み込みすると、日次ログに保存された言葉、一手、選択状態、実行状況は復元されます。火種ゲージは0から始まります。資格OSや学習ページの進捗は、それぞれのページが別のlocalStorageキーで管理しています。

## 開発時の注意

- 状態値 `10`・`30`・`50`・`70`・`100` は、カード、目標、励まし、終了メッセージを結ぶ共通キーです。
- HTML要素のIDはJavaScriptから参照されているため、変更時は参照箇所も確認してください。
- `cards[state].add` は、状態別のゲージ加算量として使用されています。
- 火種ゲージは0から100の範囲で動作します。
- `dailyGoals` と達成表示、終了・継続ボタンは連動しています。
- 月曜日の「今日の守る一行」は、判断力を守るための固定文言として扱っています。
- localStorageの既存キーを変更すると、直前表示の記録を引き継げなくなります。
- 日次ログの保存形式を変更する場合は、`hinotaneYuiDailyLogV1`との互換性を確認してください。
- 名言、守火、今日の一手には、同じ文言の連続表示を避ける処理があります。
- OS切替メニューと関連ページへの相対リンクを維持してください。
- 新しい機能が独立した学習体験になる場合は、`index.html`へ大きく埋め込まず、同じ階層の別ページとして追加する構成を検討してください。

## 今後の改善候補

以下は現在の実装済み機能ではなく、今後の改善候補です。

- 1週間の火種ログを残す
- 状態ごとの傾向を確認できるようにする
- 火種ゲージを日次・週次で保存する
- 月曜日は、判断力と余力を守る言葉を強める
- 土曜日は、希望負荷や副業への挑戦を支えるモードを強める
- 日曜日は、整えることと来週の自分を守るモードを強める
- 名言を365日分へ拡張する
- 文言データを専用JSONへ分離する
- Web App ManifestやService Workerによるオフライン対応を検討する
- 動きを抑える表示設定やキーボード操作時の視認性を改善する

# 社労士準備OS

## 社労士準備OSの概要

社労士準備OSは、社会保険労務士試験の本格学習に入る前に、基本用語、制度の違い、条件、数字、事例判断へ段階的に慣れるための学習OSです。

いきなり本試験レベルの長文問題へ進むのではなく、小さな〇×問題を通じて、社労士の世界の言葉と制度の全体像を身につけることを目的としています。

現在のメイン画面は `sharoshi-intro.html`、問題データは `sharoshi-intro-questions.json` で管理されています。画面とJSON上のタイトルは「社労士準備クイズ」です。

**社労士準備OSは、問題を解くだけのアプリではありません。社労士の複雑な制度を、用語・比較・条件・数字・事例へ分解し、理解の揺らぎを次の問題へ変換するための学習OSです。**

## 社労士準備OSの思想

社労士試験では、対象者、期間、年齢、原則と例外、関係する法律、類似制度との違い、「できる」と「しなければならない」の違いなど、複数の判断ポイントを同時に確認する必要があります。

そのため、次の学習順序を重視します。

**用語に慣れる → 似た制度を比べる → 条件・数字を見分ける → 事例で判断する → 本格学習へ進む**

ステージ1〜3は準備OSとしての土台作りです。ステージ4以降は、複数の判断ポイントを含む問題を通じて、「社労士準備OS」から「社労士OS」へ近づく橋渡しとして扱います。

## 基本的な使い方

1. 現在地カードで、現在のステージと進捗を確認する
2. 「今日の3問」または「10問チャレンジ」を解く
3. 回答後に、正解、解説、注意点、覚え方、公的根拠を確認する
4. 間違えた問題を別の日にも復習する
5. 全問回答と正答率の条件を満たし、次ステージの鍵を獲得する
6. 相談用情報をコピーし、苦手履歴を含めてユイへ次ステージ作成を相談する

## ステージ構成

現在はステージ1〜3に各30問、合計90問が登録され、ステージ1〜3が解放済みです。ステージ4・5は未解放で、問題データもまだありません。

### ステージ1：基礎用語・制度の入口

労働基準法、労災保険、雇用保険、健康保険、年金などの基本用語へ慣れる段階です。本格学習前の心理的な重さを下げ、社労士の世界の言葉へ触れることを目的とします。

### ステージ2：比較・混同対策

法定労働時間と所定労働時間、労災保険と健康保険、基本手当と傷病手当金、国民年金と厚生年金、第1号・第2号・第3号被保険者などを比較し、混同を減らす段階です。

### ステージ3：条件・例外・数字対策

6時間超、8時間超、6か月・8割、10日・5日、2年12か月、1年6か月、20歳以上60歳未満、週20時間以上などを、対象者や例外と組み合わせて確認する段階です。

### ステージ4：事例・科目横断

短い事例から関係する法律や制度を判断し、1問の中にある複数の判断ポイントを見分ける構想です。準備OSから社労士OSへ近づく橋渡しとして、本試験に近い思考へ少しずつ慣れることを目的とします。

現在は0問・未解放です。将来は30問より増やし、60問程度へ拡張することを検討します。

### ステージ5：最新公式・本番準備

現行コード上の名称です。到達時点の法改正、試験要項、公表情報、苦手履歴を確認してから作成する最終ステージとして定義されています。

将来は「本格学習前ミニ模試・苦手変換」として、本番形式、選択式・択一式、苦手問題の別表現や事例問題への変換、本格学習へ進むための判断ゲートを検討します。

## 実装済みの機能

- 今日の3問
- さらに3問
- 10問チャレンジ
- 同一セッション内で重複しない問題選択
- 未出題問題と直近に出した問題を考慮した出題
- 間違えた問題の復習と、直後の連続出題を避ける制御
- 基本用語30件の一覧表示
- 今日・累計の回答数、正答率、未出題数、間違い数の表示
- 現在ステージ、解放済みステージ、未解放ステージの表示
- 全問回答と正答率80%以上による鍵獲得判定
- 回答後の正解、解説、注意点、覚え方、公的根拠表示
- 次ステージ相談用情報のクリップボードコピー
- 火種ユイ、第二種衛生管理者資格OS v2へのOS切替メニュー

鍵獲得は表示上の到達判定です。次ステージは自動解放されず、`stages[].unlocked` と問題データを更新して解放します。

苦手分野は専用画面には表示されず、相談用コピーを作る際に、現在の間違いIDから分野別に集計されます。

## 問題データの構造

トップレベルには、次の項目が存在します。

- `version`
- `title`
- `verifiedAt`
- `stages`
- `terms`
- `questions`

`stages` には、`id`、`name`、`objective`、`unlocked`、`questionCount` が含まれます。解放条件を持つステージには `unlockAccuracy` もあります。

`terms` には、次の項目があります。

- `id`
- `category`
- `term`
- `simpleDefinition`
- `example`
- `trap`
- `relatedLaw`
- `sourceType`
- `sourceTitle`
- `sourceUrl`
- `verifiedAt`

問題データはステージによって生データの形式が異なります。

- ステージ1：`id`、`termId`、`stage`、`category`、`statement`、`answer`、`explanation`、`memoryTip`
- ステージ2：`id`、`stage`、`category`、`term`、`question`、`statement`、`answer`、`explanation`、`trap`、`memory`、`memoryTip`、公式根拠項目
- ステージ3：`id`、`stage`、`category`、`term`、`question`、`answer`、`explanation`、`trap`、`memory`、`sourceType`、`sourceTitle`、`sourceUrl`、`verifiedAt`

ステージ1の根拠情報は、`termId` で対応する用語データから取得します。読み込み時に `question` は `statement`、`memory` は `memoryTip` へ正規化されます。

## 保存

学習記録は、localStorageキー `sharoshiIntroProgressV1` に保存されます。

現在保存される情報は次のとおりです。

- 累計回答数
- 累計正解数
- 間違えた問題ID
- 最終学習日
- 直近出題ID
- 最近の出題ID
- 出題済み問題ID
- 今日の日付と回答数
- 間違えた問題ごとの復習状況
- ステージ別の回答数、正解数、回答済み問題ID

間違えた問題には、異なる学習日に正解した回数と最終正解日が保存されます。不正解を挟まず、異なる日に2回正解すると間違いリストから外れます。必ずしも連続した暦日である必要はありません。

苦手分野、ステージ解放状態、鍵獲得状態は独立して保存されません。苦手分野は間違いIDから、解放状態はJSONから、鍵はステージ進捗から都度計算されます。

現在保存されない情報は次のとおりです。

- 個別回答の時系列ログ
- 迷って正解
- 勘で正解
- 曖昧だった問題
- 手動の苦手登録
- 用語の閲覧履歴
- 途中のセッション位置

## 苦手・揺らぎデータの扱い

現行版で正式に記録される理解の揺らぎは「不正解」です。

「迷って正解」「勘で正解」「曖昧だった」「苦手登録」は、今後正式に記録することを検討している改善候補です。現在の実装では保存されません。

将来は、これらの履歴を次のような問題へ変換します。

- 同じ知識を別表現で出す
- 条件を変える
- 数字を変える
- 事例問題にする
- 似た制度との比較問題にする
- 本番風のひっかけ問題にする
- 1問の中に複数の判断ポイントを入れる

社労士準備OSでは、間違いを記録するだけでなく、間違い方を次の問題へ変換することを重視します。

## 開発時の注意

- `homeView`、`questionView`、`resultView`、`termsView`、各ボタン・統計・ステージ表示・解説欄のIDはJavaScriptから直接参照されています。
- 問題IDは重複禁止で、保存履歴を結ぶ永続キーです。公開済みIDの変更・再利用・削除は、復習履歴を壊す可能性があります。
- ステージIDは1〜5です。現在地は、問題を持つ解放済みステージのうち最大のIDから決まります。
- 鍵条件は「全問題IDを1回以上回答」と「そのステージの全回答に対する正答率80%以上」です。
- localStorageキーを変更する場合は、`sharoshiIntroProgressV1` からの移行処理が必要です。
- 現在の検証処理は、用語30件・問題90件・ステージ1〜3各30問に固定されています。ステージ4追加時は `validateData()` も更新する必要があります。
- 現在はステージ4以降の解放を拒否する検証があります。ステージ追加時は、解放条件、公式根拠の必須項目、問題数検証も同時に見直します。
- `DATA_URL` のキャッシュ回避文字列は、JSON更新時に変更します。
- 現行の出題対象判定はステージ5を除外しています。ステージ5実装時は `getUnlockedStageIds()` の条件も変更します。
- OS切替メニュー、相対リンク、スマホ表示、既存履歴、間違いの別日復習処理を維持します。

## 他OSとの関係

火種ユイの `index.html` から、OS切替メニューで社労士準備OSへ移動できます。社労士準備OSからは、火種ユイと第二種衛生管理者資格OS v2へ移動できます。衛生管理者OS側にも社労士準備OSへのリンクがあります。

AI会議室は、火種ユイから開き、火種ユイへ戻る独立ページです。社労士準備OSとの直接リンクや学習履歴の共有はありません。

各OSは、独立したHTML・JSON・localStorageキーで状態を管理します。

## 今後の改善候補

以下は、現在の実装済み機能ではなく、今後の改善候補です。

- ステージ4を60問程度に拡張する
- ステージ4から、1問に複数の判断ポイントを入れる
- ステージ5で本番形式に近づける
- 選択式風問題を追加する
- 択一式風問題を追加する
- 苦手履歴をもとに週次で問題を更新する
- 「迷って正解」「勘で正解」「曖昧だった」を正式に記録する
- 別日に2回「理解して正解」した問題を苦手卒業候補にする
- 問題データをステージ別JSONへ分離する
- 学習ログを週次で確認できるようにする
- 本格的な「社労士OS」へ移行するか判断するゲートを作る

# 第二種衛生管理者 資格OS v2

## 概要

第二種衛生管理者 資格OS v2は、第二種衛生管理者試験に向けて、基礎知識から本番形式・苦手克服までを段階的に学習する資格学習OSです。

単なる〇×クイズではなく、ステージごとに学習目的を分け、不正解・迷い・勘・苦手登録を問題ID単位で記録し、復習やステージ5の週次更新に利用します。

現在のメイン画面は `hygiene-os-v2.html`、問題データは `hygiene-os-v2-questions.json` で管理されています。

**第二種衛生管理者 資格OS v2は、問題を解くだけのアプリではありません。関係法令・労働衛生・労働生理を段階的に学び、不正解・迷い・勘・苦手登録という理解の揺らぎを、次の問題へ変換するための資格学習OSです。**

## 資格OSの思想

この資格OSの目的は、問題数をこなすことだけではありません。

ユーザーがどの分野で迷い、どの表現に引っかかり、どの知識が曖昧なのかを見つけることを重視します。

**基礎を固める → 比較する → 例外やひっかけを見抜く → 事例で判断する → 最新公式情報と苦手履歴で仕上げる**

ステージ1〜4は、理解度と苦手傾向を見つける診断フェーズです。

ステージ5は、ステージ1〜4で見えた弱点を、別表現、別条件、事例、本番形式で確認する最終調整フェーズです。

**ステージ5は、暗記の仕上げではなく、判断の仕上げです。**

## 基本的な使い方

1. 現在地カードで、現在のステージ、解放状態、回答数、正答率を確認する
2. 「今日の3問」「さらに3問」「10問チャレンジ」などを開始する
3. 回答後に、正解、解説、ひっかけポイント、覚え方を確認する
4. 「理解して正解」「迷ったが正解」「勘で正解」「不正解」を記録する
5. 間違えた問題、復習待ち、苦手問題を解き直す
6. 全問回答と正答率の条件を満たし、次のステージの鍵を獲得する
7. 自分で鍵を使って次のステージを解放する
8. ステージ5では本番30問に取り組み、週次更新用情報をコピーしてユイへ相談する

## ステージ構成

| ステージ | 名称 | 問題数 | 目的 |
|---|---|---:|---|
| 1 | 基礎 | 30問 | 基本用語・数字・役割を理解する |
| 2 | 比較・混同対策 | 19問 | 似た制度・数字・用語を区別する |
| 3 | 例外・ひっかけ | 14問 | 例外・条件・数値の違いを判断する |
| 4 | 事例・本番準備 | 18問 | 短い事例から、誰が・いつ・何を行うか判断する |
| 5 | 最新公式・本番仕上げ | 30問 | 苦手履歴をもとに、別表現・別条件・本番形式で確認する |

ステージ1〜3は、そのステージの全問題へ1回以上回答し、ステージ正答率80%以上になると鍵を獲得します。

ステージ4は、全問題へ1回以上回答し、正答率85%以上になるとステージ5を開ける状態になります。

条件達成だけでは次のステージは自動解放されません。ユーザーが「鍵を使って解放する」または「ステージ5を開く」を押したときに解放します。

## 実装済みの機能

- 今日の3問
- さらに3問
- 10問チャレンジ
- 間違えた問題
- 苦手克服
- 用語・解説を見る
- 現在ステージ、解放済みステージ、未解放ステージの表示
- ステージ別の回答数、正答率、未出題数、間違い数、苦手数の表示
- 累計回答数と最終学習日の表示
- 全問回答と正答率による鍵獲得判定
- ユーザー操作によるステージ解放
- 同一セッション内で問題IDが重複しないセッションキュー
- 未回答、出題間隔、間違い、苦手を考慮した出題
- 「理解して正解」「迷ったが正解」「勘で正解」「不正解」の記録
- 手動の苦手登録と解除
- 別日に2回連続で「理解して正解」した問題を、間違い・復習待ちから外す処理
- ステージ5の本番30問と五肢択一
- ステージ5の全体正答率と3分野別正答率
- ステージ5の本番準備完了判定
- ステージ5週次更新依頼のクリップボードコピー
- コピーが許可されない場合の選択可能な依頼文表示
- 旧版履歴の一度限りの取り込み
- 取り込み前のlocalStorageバックアップと元履歴の保持
- 火種ユイ、社労士準備クイズへのOS切替メニュー

ステージ1〜4では通常の学習モードを使用します。ステージ5では「本番30問」「復習待ちを解く」「用語・解説を見る」を使用します。

## 問題データ

トップレベルには、次の項目があります。

- `schemaVersion`
- `title`
- `sourceDataset`
- `auditDate`
- `newQuestionCount`
- `targetPerStage`
- `verifiedShortageCount`
- `stages`
- `questions`
- `stage5`

`version` やトップレベルの `verifiedAt` はありません。データ全体の監査日は `auditDate` で管理されています。

ステージ1〜4は、トップレベルの `questions` に81問を収録しています。共通する主な項目は次のとおりです。

- `id`
- `stage`
- `category`
- `theme`
- `question`
- `answer`
- `explanation`
- `trap`
- `memory`

問題によって、`choices`、`year`、`month`、`sourceType`、`sourceTitle`、`sourceUrl`、`sourceQuestion`、`verifiedAt`、`legacyStage`、`originality` などを持ちます。

ステージ1〜4のうち80問は真偽値の `answer` を使用し、選択肢がない場合は読み込み時に〇・×へ正規化されます。1問は数値の `answer` と五つの `choices` を使用します。

ステージ5は `stage5.questions` に30問を収録しています。全問が次の形式です。

- `id`
- `stage`
- `category`
- `theme`
- `question`
- 5件の `choices`
- 0始まりの `correctIndex`
- `explanation`
- `trap`
- `sourceType`
- `sourceTitle`

ステージ5には現在、`answer`、`memory`、`sourceUrl`、問題単位の `verifiedAt` はありません。

`term` と `statement` は、現在の衛生管理者v2のJSONには存在しません。

一部のステージ1〜4問題には `wrongCount`、`correctCount`、`weak`、`lastAnsweredAt` がありますが、実際の学習履歴はlocalStorageの `questionStats` が基準です。

## 保存

主な学習状態は、localStorageキー `hygieneQualificationOSV2StateV1` に保存されます。

現在保存される情報は次のとおりです。

- 累計回答数
- 最終学習日
- 現在ステージ
- 解放済みステージ
- 鍵獲得状態
- ステージ5を開ける状態
- 最近出題した問題ID
- 当日に出題した問題ID
- ステージごとの直前キュー
- 途中セッションのステージ、モード、キュー、位置、正解数
- 問題IDごとの回答回数、正解数、不正解数
- 問題IDごとの迷い回数、勘の回数、理解正解数
- 理解正解の連続数と最終理解日
- 最終回答結果と最終回答日
- 間違い状態
- 復習待ち状態
- 手動苦手状態

累計正解数、ステージ別回答数、ステージ別正解数、ステージ別正答率、回答済みID一覧、間違い・迷い・勘・苦手ID一覧は、独立した値や配列としては保存しません。

これらは、問題IDごとの `questionStats` に保存された回数やフラグから都度計算します。回答済みかどうかは `attempts > 0` で判定します。

現在保存されない情報は次のとおりです。

- 個別回答を並べた時系列ログ
- 「曖昧だった」という独立した理解度
- 用語・解説の閲覧履歴
- 週次更新用文章のコピー履歴
- 週ごとの成績スナップショット
- 問題データを更新した履歴
- クラウド上の学習履歴

週次更新用文章は保存せず、ボタンを押した時点の学習状態から生成します。

旧版履歴の取り込みには、次の別キーを使用します。

- `hygieneQualificationOSV2MigrationBackupV1`
- `hygieneQualificationOSV2MigrationDoneV1`

元の旧版履歴は削除せず、取り込み前の内容をバックアップし、同じ取り込みを繰り返さないようにします。

## 苦手・揺らぎデータ

不正解は `wrongActive` と `reviewActive`、迷い・勘は各回数と `reviewActive`、手動苦手は `manualWeak` で管理します。

2回以上不正解した問題、または迷いと勘の合計が2回以上の問題も、苦手問題として判定されます。

「迷ったが正解」「勘で正解」「不正解」は理解済みとして扱わず、復習待ちへ残します。

別の日に2回連続で「理解して正解」を記録すると、`wrongActive` と `reviewActive` が解除されます。現在は「卒業候補」という別の状態を保存・表示するのではなく、自動的に復習対象から外す実装です。

現在のアプリは、理解の揺らぎを記録し、週次更新依頼文へ反映するところまで実装しています。

同じ知識を別表現、別条件、数字変更、事例、比較、本番風のひっかけへアプリ自身が自動変換する機能は、現在は実装していません。

## ステージ5と週次更新

ステージ5は、関係法令、労働衛生、労働生理を各10問、合計30問収録しています。

本番準備完了の条件は次のとおりです。

- 全30問へ1回以上回答
- 全体正答率80%以上
- 関係法令、労働衛生、労働生理がそれぞれ40%以上
- 復習待ちが5問以下

条件を満たすと、次のメッセージを表示します。

> 本番準備完了。残りは迷い・勘・不正解の圧縮です。

「ユイへステージ5週次更新を相談する」では、次の情報を生成します。

- ステージ5の正答率
- 関係法令の正答率
- 労働衛生の正答率
- 労働生理の正答率
- 間違えた問題ID
- 迷った問題ID
- 勘で正解した問題ID
- 苦手テーマ
- 最終学習日
- ユイへの更新依頼文

現在は、週次更新用情報の生成とコピーまで実装済みです。

毎週土曜日の自動実行、問題の自動生成、JSONの自動差し替えは実装していません。公式情報と苦手履歴を確認したうえで、手動で問題データを更新する運用です。

## 開発時の注意

- `currentLocationTitle`、`stageList`、`studyPanel`、`questionView`、`confidencePanel`、`feedback`、`keyPanel`、`finalReadyPanel`、`stage5StudyModes`、`copyStage5WeeklyButton`、`migrationButton` などはJavaScriptから直接参照されています。
- HTML要素のIDを変更する場合は、`getElementById()` とイベント登録側も同時に更新します。
- ステージIDは1〜5です。
- 問題IDは全問題を通して重複禁止であり、localStorageの履歴を結ぶ永続キーです。
- 公開済み問題IDの変更、再利用、削除は、既存の回答履歴や復習状態を切り離す可能性があります。
- ステージ1〜3の鍵条件は、全問題へ1回以上回答し、ステージ正答率80%以上です。
- ステージ4からステージ5へ進む条件は、全問題へ1回以上回答し、正答率85%以上です。
- 鍵条件を満たしても自動解放せず、ユーザーの解放操作を残します。
- `reviewActive`、`wrongActive`、`manualWeak`、`understoodStreak` の意味を維持します。
- `correctIndex` は0始まり、ステージ1〜4の数値 `answer` は選択肢番号として正規化されるため、形式を混同しないようにします。
- 起動時に、問題IDの重複、ステージ範囲、ステージ5の30問、五肢択一、各分野10問を検証します。
- ステージ5は `stage5.questions` に置き、読み込み時にステージ1〜4の `questions` と結合します。
- `hygieneQualificationOSV2StateV1` を変更する場合は、既存データを引き継ぐ移行処理が必要です。
- 旧版履歴の移行では、バックアップ、ID一致確認、重複実行防止、元履歴の保持を維持します。
- 出題キューでは、同一セッション内の重複防止と、未回答、出題間隔、間違い、苦手の優先順位を維持します。
- `DATA_URL` のキャッシュ回避文字列は、JSON更新時に変更します。
- 週次更新コピーは、クリップボードAPIと、選択可能なテキストを表示する代替処理の両方を維持します。
- OS切替メニュー、相対リンク、スマホ表示、既存履歴を維持します。

## 他OSとの関係

火種ユイの `index.html` から、OS切替メニューで第二種衛生管理者 資格OS v2へ移動できます。

衛生管理者v2のOS切替メニューからは、火種ユイと `sharoshi-intro.html` の社労士準備クイズへ移動できます。

旧版の `quiz.html` は、ファイルと学習履歴を残しています。現在、衛生管理者v2のOS切替メニューには旧版へのリンクを表示していません。

`ai-meeting.html` への直接リンクは衛生管理者v2にはありません。AI会議室は火種ユイから開く独立ページです。

各OSは、独立したHTML、JSON、localStorageキーで状態を管理します。衛生管理者v2と社労士準備OSの学習履歴は共有しません。

# 開発運用ルール

Codexは、第二脳ユイのAIチームにおける実装・検証・品質管理担当として運用します。

ユイが思想・目的・設計を整理し、Codexはそれを安全にコードへ変換します。

## 基本姿勢

- 変更は小さく、安全に行います。
- 既存機能、学習データ、同期データを壊さないことを優先します。
- 実装前に影響範囲を確認します。
- 不明点を推測で埋めません。
- 問題がある場合は原因を切り分けます。
- ローカルで動くだけでは完了としません。
- スマホ表示、GitHub Pages、同期機能まで必要に応じて確認します。
- 大量の機能を一度に変更せず、小さく試してから広げます。
- 使わない情報や不要な複雑さを増やしません。

## 作業開始時の報告

作業前に、次の3点を簡潔に示します。

1. 今回変更するもの
2. 変更しないもの
3. 主なリスク

## 作業中の扱い

- 同じ確認を長時間繰り返しません。
- 10分以上同じ原因調査や検証が続く場合は、一旦止まり、完了したこと、現在確認していること、解決していないこと、次に試すことを報告します。
- ユーザーの指示なく作業範囲を広げません。

## 完了条件

必要な範囲で、次を確認してから完了とします。

- 実装完了
- 構文またはデータ構造の確認
- 既存機能への影響確認
- スマホ幅での表示確認
- 必要な場合はGitHubへcommit・push
- 必要な場合はGitHub Pagesの公開版確認
- 必要な場合はbuildVersion更新

## 完了報告

完了時は、変更概要だけをコピーしやすい形式で簡潔に報告します。

報告には、変更、追加、確認済み、変更していないもの、未確認・注意点、GitHub状況、次回改善候補を含めます。

次回改善候補は1つだけにします。

## 信条

変更は小さく、安全に。壊さず育てます。
